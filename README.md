# Ковадло

Чисте Python-ядро для параметричного моделювання будівель. Без графіки,
без UI — лише геометрія, дані й розрахунки, які потім можна обгорнути
будь-яким рендерером.

## Модуль 1: кімната і стіни

- `Point(x, z)` — точка плану в міліметрах.
- `snap_angle` / `snap_point` — прив'язка кута до кроку 15° (як під час
  малювання стіни в CAD: клікнув приблизно — кут "прилип" до сітки).
- `polygon_area` / `polygon_perimeter` — площа (формула Гаусса) і периметр
  довільного полігонального контуру; контур замикається автоматично.
- `Wall` — стіна: дві точки + висота + товщина + матеріал; товщина
  зберігається в профілі (`RectangularProfile`).
- `Room` — контур + список стін; автоматично рахує площу підлоги та
  площу кожної стіни (`Room.from_contour(...)` будує стіну на кожному
  ребрі контуру одним викликом).

## Архітектура на майбутнє

Базова сутність — `Element`: **дві точки + профіль + матеріал + кут**.
`Wall` — це `Element` з доданою висотою. Профіль перерізу (`Profile`) —
окрема абстракція, тому нові типи перерізів додаються без зміни
`Element`, `Wall` чи `Room`. На доказ цього в `kovadlo/profile.py` вже є
не тільки `RectangularProfile`, а й металопрофілі:

- `SteelChannelProfile` — швелер,
- `SteelAngleProfile` — кутник,
- `SteelPipeProfile` — труба.

`tests/test_profile.py::test_element_accepts_any_profile_without_core_changes`
явно перевіряє, що `Element` працює з будь-яким з цих профілів без жодних
змін у своєму коді.

## Модуль 2: покриття плиткою

- `Surface` — поверхня для покриття: `Surface.from_room_floor(room)` (підлога)
  або `Surface.from_wall(wall)` (стіна, розгорнута в прямокутник) — береться
  напряму з модуля 1.
- `Tile` — плитка: ширина, висота, назва, колір.
- `Grout` — фуга: ширина шва в мм, колір.
- `TileLayout` — розкладка: стартова точка, зсув рядів (`RowOffset.NONE` 0%,
  `HALF` 50%, `THIRD` ⅓), кут (0 або 45°).
- `calculate_tiling(surface, tile, grout, layout, tiles_per_package=...)` →
  `TilingResult` з:
  - `whole_tiles_count` — кількість цілих плиток;
  - `cuts` / `cuts_summary()` — список підрізок з точним розміром кожної
    (ширина x висота в мм), згрупований за розміром;
  - `total_tiles_needed` — загальна кількість плиток (цілі + підрізки);
  - `packages_needed` — кількість упаковок;
  - `reserve_tiles` — запас (за замовчуванням 10%) **окремим числом**, не
    входить у `total_tiles_needed`/`packages_needed`;
  - `grout_area_m2` — площа фуги для розрахунку суміші.
- `format_report(...)` — текстовий звіт (жодної графіки).

**Як рахуються неprямокутні кімнати:** підлога з виступом розкладається
(`Surface.rectangles()`) на прямокутні зони (`decompose_rectilinear_polygon`
у `geometry.py`), кожна зона тайлиться в спільній системі координат
розкладки через точне відсікання опуклих полігонів (`clip_convex_polygon`,
Сазерленд-Ходжмен) — це дає точний розмір кожної підрізки, а не наближення.
Свідомий компроміс: межа між зонами декомпозиції (там, де контур розбито,
а не там, де реально стоїть стіна) теж ріже плитку — детальніше в
docstring `kovadlo/tiling.py`.

## Модуль 3: візуалізація

Локальний веб-сервер на чистому Python (лише `http.server` зі стандартної
бібліотеки, без залежностей) + одна HTML-сторінка з малюванням на canvas.
**Ядро (модулі 1-2) при цьому не змінене — модуль 3 лише читає його публічні
функції.**

- `web/server.py` — HTTP-сервер і JSON API (`/api/snap`, `/api/room`,
  `/api/tiling`); стан (поточна кімната) — у пам'яті процесу.
- `web/static/index.html` — та сама одна сторінка: вид зверху (контур,
  товщина стін, розміри кожної стіни в мм), вид розгортки обраної стіни
  (або підлоги) з розкладкою плитки, панель збоку з текстовим звітом
  модуля 2. Малювання контуру пальцем/мишею (тап — точка, прив'язка до
  15°, тап по першій точці замикає), панорама перетягуванням, масштаб
  щипком або колесом миші.
- `web/tiling_render.py` — окремий рендер-шар: ядро (`calculate_tiling`)
  свідомо не зберігає позицію кожної плитки (для підрахунку вона не
  потрібна), тож для canvas тут — окрема функція, яка читає ті самі
  публічні примітиви ядра (`clip_convex_polygon`, `rotate_point`,
  `Surface.rectangles`) і повертає контур КОЖНОЇ плитки (а не лише
  bounding box — тому підрізки при куті 45° на екрані мають справжню,
  не обов'язково прямокутну форму). Узгодженість із підрахунком ядра
  перевірена тестом `test_render_totals_match_calculate_tiling`.

Запуск:

```bash
python -m web.server            # порт 8765 за замовчуванням
python -m web.server 9000       # або свій порт
```

Відкрити `http://127.0.0.1:8765/` у браузері (працює й на телефоні в
локальній мережі за IP машини).

## Модуль 4: електропроводка

Розрахунок кіл електромережі — теж без графіки, лише текстовий звіт. Нові
файли додані поруч із модулями 1-2 в `kovadlo/` (ядро розширене, наявні
файли модулів 1-3 не змінені).

- `ConsumptionPoint` — точка на плані: `PointKind.SOCKET/SWITCH/LIGHT/
  STOVE/BOILER/PANEL` (розетка/вимикач/світильник/плита/бойлер/щиток) +
  позиція (`Point` з модуля 1) + потужність у Вт (типова за замовчуванням
  з `DEFAULT_POWER_W`, завжди можна перевизначити).
- `CableRoute` / `build_route(panel, waypoints)` — полілінія траси кабелю
  від щитка до точки; `build_route` прив'язує кожен відрізок до кута,
  кратного 90°, **перевикористовуючи** `kovadlo.snap_point` з модуля 1
  (той самий механізм, що й прив'язка кутів контуру кімнати, лише з
  кроком 90° замість 15°).
- `Group` — група точок на одному апараті захисту: сумарна потужність,
  розрахунковий струм (230 В однофазна / 400 В трифазна), сумарна довжина
  кабелю (із запасом на підключення на кожну трасу) і найдовша траса
  (визначальна для падіння напруги).
- `calculate_group(group)` → `GroupCalculation`: номінал автомата
  (`select_breaker_rating_a`, Ib ≤ In), переріз жили (`select_cross_section_mm2`,
  одночасно Iz ≥ In і падіння напруги ≤ 3%, `voltage_drop_percent`),
  потреба в ПЗВ/дифавтоматі (`rcd_required_for_kinds`).
- `WiringPlan` (щиток + групи) → `format_wiring_report(plan)` — звіт по
  кожній групі + специфікація кабелів на закупівлю (переріз, довжина).

**Норми:** PN-HD 60364 (Польща) — конкретні частини процитовані прямо в
docstring `kovadlo/electrical_norms.py` (4-41 — ПЗВ, 4-43 — координація
Ib ≤ In ≤ Iz, 5-52 — струмонесуча здатність і падіння напруги). Табличні
значення (струмонесуча здатність, ряд перерізів/автоматів) — типові
орієнтовні інженерні значення для ілюстрації методики, **не** дослівна
виписка з чинного тексту норми — це чесно зазначено в тому ж docstring:
перед реальним монтажем звірте з чинною редакцією й довірте розрахунок
електрику.

## Модуль 5: візуалізація проводки

Третя вкладка «Електрика» в тій самій сторінці модуля 3 — поверх плану
кімнати. Ядро (модулі 1-4) не змінене; додано лише нові API-обробники в
`web/server.py` і новий режим у `web/static/index.html` (`web/` — це сам
шар візуалізації, а не ядро, тому він і розширюється з кожним модулем).

- Розстановка точок споживання: обираєш тип (розетка/вимикач/світильник/
  плита/бойлер/щиток), тап на плані ставить `ConsumptionPoint` (ядро,
  модуль 4) через `POST /api/electrical/point`.
- Малювання траси: тап додає вигин траси з прив'язкою до 90° —
  **перевикористовує** той самий `POST /api/snap`, що й контур кімнати в
  модулі 3, лише з `step=90`; довжина траси показується наживо під час
  малювання (рахується на клієнті з уже прив'язаних точок).
- Групи: точка прив'язується до групи (нова чи наявна, фаза 230/400 В);
  на плані група позначається кольором (стабільним у межах сесії),
  товщина лінії траси відповідає перерізу жили з розрахунку ядра —
  поки групу не порахувано (не вистачає траси в когось із учасників),
  лінія пунктирна.
- Панель збоку: живий звіт з модуля 4 (`GET /api/electrical/report` →
  `format_wiring_report`) — групи, струми, перерізи, автомати, ПЗВ,
  специфікація кабелів на закупівлю.
- Експорт звіту в `.txt`: суто клієнтська дія (Blob + `<a download>`),
  без окремого серверного ендпоінта.
- Переставити щиток можна повторним тапом — усі вже намальовані траси
  автоматично перераховуються від нового місця (сервер зберігає лише
  точки траси ПІСЛЯ щитка й щоразу підставляє актуальну позицію щитка
  через `build_route` з ядра).

## Модуль 6: друковані плати та схеми

Мікроелектроніка — компоненти, схема (логічний рівень) і плата (фізичний
рівень). Нові файли (`pcb_*.py`) додані поруч із модулями 1-5 в
`kovadlo/`, наявні файли не змінені. Без графіки — лише розрахунок і
текстовий звіт.

- `Component`/`Footprint`/`Pin` (`pcb_component.py`) — резистор,
  конденсатор, діод, транзистор, мікросхема, роз'єм, світлодіод: назва,
  тип, номінал (Ом/Ф/В/А з авто-форматуванням SI-префіксом, напр. "4.7
  кОм"), посадкове місце з координатами кожного виводу. Фабрики
  стандартних посадкових місць у `pcb_footprints.py` (DIP, SOIC, THT,
  TO-92, роз'єм) — з коректною проти-годинниковою DIP/SOIC-нумерацією.
- `Netlist` (`pcb_netlist.py`) — схема: компоненти + ланцюги (`Net`) із
  типом (сигнал/живлення/земля) і списком з'єднаних виводів. Перевірки:
  `dangling_pins()` (висячі виводи) і `power_ground_shorts()` (коротке
  замикання живлення на землю — вивід одночасно в ланцюгах VCC і GND).
- `Board` (`pcb_board.py`) — плата: контур (той самий полігон з модуля
  1), розміщення компонентів (координати + кут повороту), доріжки
  (`Track` — полілінія з шаром і ланцюгом) і перехідні отвори (`Via`).
  `build_track(...)` прив'язує кут до 45° тим самим `snap_point` з
  модуля 1, що й контур кімнати (15°) та кабельна траса (90°).
- `pcb_norms.py` — методика **IPC-2221**: ширина доріжки за струмом і
  нагрівом (`required_track_width_mm`), опір і падіння напруги на міді
  35 мкм за замовчуванням (`track_resistance_ohm`), таблиця мінімальних
  зазорів за напругою (`min_clearance_mm`). Усі табличні значення явно
  позначені як орієнтовні — з посиланням на конкретний розділ методики
  (4-41/4-43/5-52-подібна структура IPC-2221) прямо в docstring.
- `pcb_checks.py` — **ratsnest** (`unrouted_connections`): чи кожне
  з'єднання нетлиста фізично реалізоване доріжками/via (граф зв'язності
  через систему неперетинних множин); і **зазори** (`clearance_violations`):
  мінімальна відстань відрізок-відрізок між доріжками різних ланцюгів
  на одному шарі, звірена з таблицею IPC-2221.
- `format_board_report(...)` (`pcb_report.py`) — зведений текстовий
  звіт: специфікація компонентів на закупівлю (BOM, згруповано за
  типом/номіналом), перевірка схеми, доріжки з розрахунком, ratsnest,
  зазори.

## Модуль 7: база матеріалів

Наскрізний модуль — ним користуються стіни (модуль 1), плитка/фуга
(модуль 2), електрика (модуль 4) і плати (модуль 6). **Ядро модулів 1-6
не змінене**: оскільки `Wall.material` уже має тип `kovadlo.materials.Material`
(лише назва + густина), прив'язка до бази реалізована як **посилання за
іменем**, а не новим полем у наявних класах:

- `MaterialSpec.to_core_material()` (`material_spec.py`) дає сумісний з
  ядром `Material` — саме це передається в `Wall`/`Room.from_contour`;
  `MaterialDatabase.find_by_name(...)` (`material_database.py`) знаходить
  повний запис назад за тим самим іменем. Так само `conductor_resistance_ohm(...)`
  (`material_compare.py`) дає опір дорожки/кабелю з питомого опору
  запису бази — це і є "прив'язка" для дорожки (модуль 6) і кабелю
  (модуль 4), без нового поля в `Track`/`CableRoute`.
- `MaterialSpec` — назва, категорія, стандартне позначення, фізичні
  властивості (густина, міцність на стиск/розтяг, теплопровідність,
  питомий опір, ТКЛР, температура плавлення), практичні (сфера
  застосування, вулиця/приміщення, морозостійкість, водостійкість,
  витрата) і ціна (`PriceInfo`: за кг/м²/м³/упаковку, з датою й
  регіоном — **явно позначена як орієнтовна**).
- `material_seed.py` — 23 ілюстративні записи в 7 категоріях завдання
  (бетони й розчини, гіпс і сухі суміші, клеї для плитки C1/C2·S1/S2,
  фуги цементні/епоксидні, метали, ізоляція, провідники) — усі значення
  й ціни з явним застереженням про орієнтовність і джерело (EN-норми,
  довідники) прямо в docstring.
- `MaterialDatabase` (`material_database.py`) — пошук за іменем/категорією,
  довільний фільтр і готові фільтри ("теплопровідність менша за X",
  "морозостійкий", "міцність більша за Y").
- `select_materials(db, SelectionCriteria(...))` (`material_selection.py`) —
  підбір під задачу (де, вулиця/приміщення, морозостійкість,
  водостійкість, міцність, теплопровідність) з переліком причин для
  кожного результату; `select_tile_adhesive_for_balcony(db)` —
  готовий приклад типової задачі.
- `compare_for_thermal_resistance(...)` (`material_compare.py`) —
  порівняння двох матеріалів за товщиною й орієнтовною ціною за м² для
  однакового потрібного опору теплопередачі стіни (R = d/λ).

## Модуль 8: інженерні системи будівлі

П'ять підсистем, той самий підхід, що й модуль 4 (точки на плані +
траси + розрахунок), глибоко пов'язаний з модулями 1 і 7. Ядро модулів
1-7 не змінене.

- **8.1 Освітлення** (`lighting_norms.py`, `lighting.py`) —
  `LightFixture` (потік, потужність, кут розсіювання, колірна
  температура), розрахунок освітленості методом коефіцієнта
  використання (E = Φ·UF·MF/S), орієнтовні норми EN 12464-1 за
  призначенням кімнати, підбір кількості світильників
  (`plan_lighting`). `lighting_group(...)` перетворює світильники на
  `ConsumptionPoint` і збирає `Group` модуля 4 — "світильники стають
  групою в проводці" без зміни ядра модуля 4.
- **8.2 Вентиляція** (`ventilation_norms.py`, `ventilation.py`) —
  `Duct` (полілінія з `snap_point`, крок 90°, переріз круглий/
  прямокутний, матеріал — `MaterialSpec` модуля 7), потрібний
  повітрообмін (фіксована витяжка для "мокрих" приміщень або кратність
  повітрообміну), швидкість і втрати тиску (Дарсі-Вейсбах), підбір
  діаметра й вентилятора.
- **8.3 Кліматизація** (`climate_norms.py`, `climate.py`) —
  тепловтрати трансмісією (Q=U·A·ΔT, U — з `insulation.py`, площі — з
  модуля 1) і на вентиляцію (пов'язано з 8.2), підбір потужності
  радіатора/кондиціонера.
- **8.4 Утеплення** (`insulation.py`) — опір теплопередачі стіни шар за
  шаром (`WallLayer` з `MaterialSpec` модуля 7), порівняння з
  орієнтовною нормою WT2021, підбір товщини утеплювача й ціна за м²
  (`kovadlo.material_compare`), спрощена перевірка ризику конденсату
  (точка роси, формула Магнуса) — з чесним застереженням, що це
  скринінг за температурою, а не повний аналіз Ґлазера.
- **8.5 Пожежна безпека** (`fire_safety_norms.py`, `fire_safety.py`) —
  `FireDetector`, автоматична розстановка по контуру кімнати (модуль 1)
  за площею покриття й максимальною відстанню, довжина шлейфу
  (петля щиток → датчики → щиток), місток до модуля 4 через

## Модуль 9: візуалізація інженерних систем

Продовження модулів 3/5 — ще 4 вкладки на тій самій сторінці, поверх
того самого плану (`state.viewTop`). Ядро (модулі 1-8) не змінене:
додано лише `web/reports.py` (текстові звіти — у модулі 8 немає готових
`format_*_report`, на відміну від модулів 2/4) і нові API-обробники в
`web/server.py`/`web/static/index.html`.

- **Освітлення** — тап ставить світильник обраного типу; кольорова

  фізичний розрахунок), справжнє число лк у панелі береться напряму з

- **Вентиляція** — малювання повітропроводу з прив'язкою 90°

- **Тепло** — тап по стіні відкриває редактор шарів: додати шар з

  товщиною. Розріз стіни малюється як пропорційна смуга з підписами
  товщини й матеріалів. Панель: R, U, норма WT2021, попередження про
  точку роси, тепловтрати стіни.
- **Пожежна безпека** — кнопка «Розставити автоматично»

## Модуль 10: тривимірна геометрія

Ядро модулів 1-9 не змінене — нові файли лише читають і перевикористовують
контури модуля 1, шари конструкції модуля 8.4 і ціни модуля 7.

- `Point3(x, y, z)` (`geometry3d.py`) — x, z як у плані модуля 1, y —
  висота; `Face` — плоска грань із площею за формулою Ньюелла (коректно
  й для похилих граней, напр. схилів даху).
- `extrude_contour_walls(contour, height)` (`extrude.py`) — контур
  кімнати → вертикальна грань на кожне ребро.
- `Wall3D` (`wall3d.py`) — стіна як об'єм: дві бічні грані симетрично
  відносно осьової лінії (`side_faces`), `inner_outer_faces(centroid)`
  визначає, яка "всередину" відносно кімнати; шари конструкції з
  модуля 8.4 (`WallLayer`) мусять у сумі давати товщину стіни; отвори
  (`Opening` — вікно/двері, `opening.py`) наскрізні через усі шари й
  зменшують `net_area_m2`/об'єм кожного шару.
- `Slab` (`slab3d.py`) — перекриття/підлога: контур на заданій висоті,
  з товщиною.
- `Roof`/`build_shed_roof`/`build_gable_roof` (`roof3d.py`) —
  односхилий і двосхилий дах над прямокутним контуром, за кутом
  нахилу; площа схилу = площа контуру / cos(кута) — перевірено як
  інваріант тестами для обох типів даху.
- `Building`/`Storey` (`building3d.py`) — список поверхів; `contours_match`
  перевіряє збіг контурів сусідніх поверхів (з точністю до зсуву
  стартової вершини й напрямку обходу).
- `room_volume_m3`/`exterior_envelope_area_m2`/`wall_material_volumes_m3`/
  `wall_material_costs_pln` (`volume_calc.py`) — об'єм кімнати (для
  вентиляції 8.2), чиста площа огороджень з вікнами (для тепловтрат 8.3),
  об'єм і орієнтовна вартість матеріалів стін (ціна — з модуля 7, через
  публічну `insulation_cost_per_m2` модуля 8, без приватних хаків).
- `Mesh`/`build_room_mesh` (`mesh_export.py`) — проста сітка (вершини +
  трикутники, віяльна тріангуляція опуклих граней) і серіалізація у
  Wavefront OBJ (мм → м) — заготовка для рендеру, який буде пізніше.

## Модуль 11: тривимірний перегляд у веб-інтерфейсі

Нова вкладка «3D» поверх наявного інтерфейсу (модулі 3/5/9, той самий
`web/static/index.html`). Ядро (модулі 1-10) не змінене — додано лише
`web/scene3d.py` (серіалізація стану сервера в JSON-опис сцени) і нові
API-обробники/фронтенд-код у `web/server.py`/`index.html`. Сам рендер —
цілком на клієнті.

- **three.js r128 з CDN, а не сирий WebGL.** Обрано як простіший і
  надійніший варіант для мобільного Chrome — не треба вручну писати
  шейдери й матричну математику, а v128 — стабільна класична
  глобальна (UMD) збірка, без переходу на ES-модулі, що спрощує
  підключення одним `<script>`-тегом без бандлера.
- **Власний орбітальний контролер камери** (азимут/полярний
  кут/радіус/ціль на сферичних координатах), а не готовий
  `OrbitControls` — щоб не тягнути ще один файл із CDN і мати точний
  контроль над потрібною семантикою жестів: **один палець — обертання
  камери, два пальці — одночасно масштаб (pinch) і панорама (зсув
  середньої точки двох дотиків)**, реалізовано на тому самому Pointer
  Events API, що й у 2D-вкладках. Кнопки швидких видів (зверху,
  спереду, ізометрія) виставляють азимут/полярний кут напряму.
- **Реальні прорізи вікон/дверей у геометрії** — це суто питання
  рендер-шару: `Opening3DState` на сервері валідується справжнім
  `Wall3D`/`Opening` ядра (модуль 10), а на клієнті кожна стіна
  будується як `THREE.Shape` з отворами (`.holes`, масив
  `THREE.Path`) і видавлюється `THREE.ExtrudeGeometry` — на відміну
  від ядра модуля 10, де отвір лише зменшує `net_area_m2` в
  розрахунках, тут дірка справжня, наскрізна.
- **Плитка — текстура-патерн, не окремі об'єкти.** Розмір плитки й
  шва беруться з `state.tiling` (модуль 2); `THREE.CanvasTexture` із
  `RepeatWrapping` малює один період патерну на 2D-canvas і повторює
  його по UV — і на підлозі, і на стінах, без окремої геометрії на
  кожну плитку (вимога продуктивності).
- **Колір поверхонь** — за категорією матеріалу з бази модуля 7
  (`MaterialDatabase.find_by_name`); якщо матеріал не знайдено в базі
  (наприклад, введений вручну текстом) — нейтральний колір за
  замовчуванням, без падіння рендеру.
- **Додатково**: кабельні траси модуля 5 — `THREE.Line` уздовж точок
  траси (`build_route`, snap вимкнено — лінія показує вже прокладений
  шлях, а не інструмент трасування); повітроводи модуля 8.2 —
  `THREE.TubeGeometry` уздовж `THREE.CurvePath`/`LineCurve3`, радіус
  труби з діаметра/перетину каналу; світильники — маленькі сфери на
  стелі плюс `THREE.PointLight` у їхній позиції.
- **Продуктивність**: панель вкладки показує
  `renderer.info.render.triangles` наживо для перевірки на телефоні;
  дах/стіни можна ховати перемикачами (`toggleRoofVisible`,
  `toggleWallsVisible`), щоб зменшити навантаження чи побачити
  інтер'єр.
- `RoofState`/`Opening3DState` на сервері — окремий стан для 3D
  (тип/кут даху, отвори по стінах), не втручається в стан модулів 1/10.

## Модуль 12: механіка та фізика руху

Ядро модулів 1-11 не змінене — нові файли поруч у `kovadlo/`, лише
`__init__.py` доповнений новими іменами (наявні рядки не чіпалися).
Жодної графіки — лише розрахунки й текстовий звіт. Усі формули —
стандартний курс опору матеріалів і теорії машин і механізмів
(джерела вказано в докстрінгах кожного файлу).

- `steel_profiles.py` — розширює `Profile` (модуль 1) новим абстрактним
  нащадком `StructProfile` із моментом інерції й моментом опору
  перерізу: кутник, швелер, двотавр, кругла й прямокутна труба, смуга,
  пруток. Швелер/двотавр — методом "суцільний прямокутник мінус
  вирізаний" (Iₓ навколо горизонтальної осі виходить однаковим для
  обох, бо залежить лише від розподілу матеріалу по висоті — перевірено
  як інваріант тестом); кутник — тонкостінне наближення двома смугами з
  теоремою Штейнера відносно спільного центроїда.
- `mechanics_norms.py` — орієнтовні модулі Юнга металів бази модуля 7
  (за іменем матеріалу, той самий підхід "посилання за іменем", що й у
  модулі 7 для `Wall.material`), прискорення вільного падіння,
  типовий коефіцієнт запасу міцності, гранична прогинистість L/250.
- `beam.py` — `Beam`: та сама ідея "дві точки + профіль + матеріал +
  кут", що й `Element` (модуль 1), але в 3D (`Point3`, модуль 10) — бо
  кут нахилу елемента відносно горизонталі/вертикалі не має сенсу на
  плоскому плані. Вага балки й конструкції (`Structure`), чотири
  класичні розрахункові схеми згину (шарнірно оперта/консоль ×
  зосереджена/розподілена сила), напруження, прогин, перевірка міцності
  й прогину з коефіцієнтом запасу (`evaluate_beam`).
- `shaft.py` — вал (вісь, довжина, діаметр, матеріал, маса) і момент
  інерції ОБЕРТОВОЇ МАСИ диска/кільця/колеса (кг·м²) — навмисно чітко
  відділено в докстрінгу від моменту інерції ПЕРЕРІЗУ (мм⁴) балки, бо
  в українській термінології обидва звуться однаково, хоч це різні
  фізичні величини.
- `transmission.py` — переведення обертів у кутову швидкість,
  потужність через момент (P = M·ω), і три типи передач (пряма,
  редуктор, ремінна) через єдине передатне число `ratio` з урахуванням
  ККД.
- `motor.py` — колекторний DC/безколекторний BLDC/кроковий: струм під
  навантаженням через сталу моменту Kt = 60/(2π·Kv), потужність,
  тепловиділення (I²R, енергетичний баланс або оцінка через ККД —
  залежно від того, що відомо). Зв'язок з модулем 4 (`PointKind.SOCKET`
  — у ядрі немає окремого типу "двигун", тож найближчий наявний, з
  реальною потужністю U·I замість типового значення розетки) і з
  модулем 6 (`motor_pcb_track_width_mm` напряму викликає
  `required_track_width_mm`, IPC-2221, за струмом двигуна).
- `kinematics.py` — лінійна швидкість колеса, час розгону (маса
  приводиться до валу колеса як I = m·r², додається до власного
  моменту інерції обертових частин), перевірка "чи вистачить моменту
  зрушити задану масу" (тягове зусилля колеса проти сили тертя/схилу).
- `mechanics_report.py` — текстові звіти: по одній балці, по всій
  конструкції (сумарна вага, список балок, що не пройшли перевірку), і
  по приводу (двигун + передача, оберти/момент на виході, струм,
  тепловиділення).

## Модуль 13: керування та логіка (автоматика)

Ядро модулів 1-12 не змінене — нові файли поруч у `kovadlo/`, `__init__.py`
доповнений (наявні рядки не чіпалися). Без графіки — лише логіка й
текстовий звіт.

- `sensors.py` — `Sensor`+`SensorKind` (кінцевик/кнопка/рух/відстань/

- `actuators.py` — `Actuator`+`ActuatorKind` (реле, контактор,

  `motor.py`.
- `controller.py` — `Controller`: прив'язка датчиків до входів,
  механізмів до виходів; `check()` — три перевірки за завданням: чи
  вистачає пінів (окремо цифрові/аналогові входи, цифрові/ШІМ виходи),
  чи сумісні напруги (з допуском до типових рейок 3.3/5/12 В), чи не
  перевищено допустимий струм на вихід (інакше — потрібне проміжне реле).
- `automation_logic.py` — декларативний рушій "умова -> дія": `Condition`
  (стан + значення входів + сплив таймера), `Action` (новий стан, виходи,
  запуск/зупинка таймера), `Scenario` (стани, правила, таймери, заборонені
  переходи). `apply_step` каскадно застосовує правила в порядку
  пріоритету (перше, що збіглося) — природний спосіб реалізувати
  аварійний стоп (правило на аварійний вхід, перше в списку, перекриває
  решту); кожне правило спрацьовує щонайбільше раз за виклик, тож цикл
  гарантовано завершується без штучного ліміту ітерацій. `find_dead_end_states`
  — статична перевірка на глухий кут (стан без жодного виходу, крім
  явно дозволених `terminal_states`); `find_forbidden_rule_violations` —
  чи є правило, яке саме веде в заборонений перехід.
- `automation_sim.py` — `run_scenario`: прогін сценарію по послідовності
  подій у часі (`SimulationStep`), журнал зміни станів/виходів по кроках
  (`SimulationResult`).
- `gate_automation.py` — приклад для тестів: автоматична брама (два
  кінцевики, кнопка, фотобар'єр безпеки, двигун через редуктор,
  під'єднаний до контролера через контактори, а не напряму — інакше
  не пройшла б перевірка струму на вихід). `gate_cycle_time_s` рахує
  час ходу через модуль 12 (`GearboxTransmission.output_rpm` +
  `wheel_linear_speed_m_s`); безпечний реверс при перекритті
  фотобар'єру під час закривання; аварійний таймаут = час циклу + запас.
- `automation_report.py` — текстові звіти: контролер, сценарій (глухі
  кути/заборонені переходи), журнал симуляції по кроках, зведений звіт
  прикладу брами.

## Модуль 14: нативний застосунок Android (APK)

Ковадло як звичайна програма на телефоні — іконка, splash-екран,
офлайн, без Termux і браузера. Новий каталог `android/` (Gradle-проєкт)
+ два нові файли у `web/` — ядро `kovadlo/` і решта `web/` не змінені.

- **Kotlin + WebView + Chaquopy (варіант А), а не переписування ядра
  на Kotlin.** Ядро (модулі 1-13, 600+ тестів) лишається без змін і
  без ризику розбіжностей із перевіреною Python-версією; наявний
  веб-інтерфейс (модулі 3/5/9/11) уже є повним UI — досатньо показати
  ту саму сторінку в `WebView`, а Python виконати не в терміналі, а
  всередині застосунку через Chaquopy. Обидва (`kovadlo/`, `web/`) без
  жодної зовнішньої залежності (лише stdlib), тож збірка не тягне
  pip-колеса під Android ABI.
- **Пакети підключені як є** — `android/pysrc/{kovadlo,web}` символічні
  посилання на корінь репозиторію (не копії): одне джерело правди для
  десктопної й мобільної версії.
- **WebView на весь екран**, локальний контент з `127.0.0.1` (сервер
  `web/server.py` запущено в застосунку через Chaquopy, `KovadloApp.kt`)
  — жодного звернення в інтернет.
- **Дозвіл лише один** — `WRITE_EXTERNAL_STORAGE` з `maxSdkVersion="28"`
  (сумісність зі старими Android; на 10+ однаково не дав би вільного
  доступу через scoped storage). Збереження/відкриття файлу проєкту на
  API 29+ — через Storage Access Framework (`ProjectFileBridge.kt`),
  що не потребує жодного дозволу взагалі.
- **`web/project_io.py`** (нове) — `export_project`/`import_project`:
  повний round-trip стану сервера (кімната, проводка, освітлення/
  вентиляція/тепло/пожежна безпека, дах і отвори) в один JSON, окремо
  від наявних `_handle_*_state` обробників (ті віддають дані для
  малювання, тут — сирі вхідні параметри для точного відновлення).
  Нові ендпоінти `/api/project/export` (GET) і `/api/project/import`
  (POST) у `web/server.py`. Плитка (модуль 2) на сервері не зберігається
  як стан — її поля з вкладки «Розгортка/плитка» серіалізуються окремо
  на клієнті (`index.html`), найкраще зусилля.
- Формат проєкту — `.json`: `{format, version, room, electrical,
  lighting, ventilation, heat, fire, roof, openings3d}` на сервері +
  `{tiling_settings}` від клієнта в загальній обгортці `kovadlo-project-full`.
- **Збірка**: у цій сесії (Termux + proot-distro Ubuntu, той самий
  телефон) реально встановлено JDK 17, Android SDK (platform 34,
  build-tools 34), Gradle 8.7 — інструментарій ставиться й працює, і
  `./gradlew :app:assembleDebug` дійшла аж до 29 виконаних задач
  (Kotlin, пакування Python через Chaquopy) — усе відпрацювало. Впала
  лише на останньому кроці, `aapt2` (компілятор ресурсів Android):
  перевірено напряму (`readelf -h`) — офіційний `aapt2` існує лише як
  x86_64-бінарник (Google не публікує linux-aarch64 build у ЖОДНІЙ
  версії аж до найновішої 9.3.2), а телефон — aarch64. Це структурне
  обмеження офіційного інструментарію Android для будь-якого
  ARM64-телефона, не разова невдача цієї сесії. Робочий шлях зібрати
  APK: `.github/workflows/android-build.yml` (GitHub Actions, x86_64
  раннер, готовий APK в артефактах) або Android Studio на ПК.
  Детальніше, з повним логом висновку, — `android/README.md`.

```bash
# тести
pytest

# приклади (модулі 1, 2, 4, 6, 7, 8, 10, 12, 13 — текстовий вивід)
python -m examples.room_with_protrusion
python -m examples.tiling_room_with_protrusion
python -m examples.wiring_apartment
python -m examples.pcb_simple_board
python -m examples.material_database_demo
python -m examples.building_systems_demo
python -m examples.building_3d_demo
python -m examples.mechanics_demo
python -m examples.automation_demo

# візуалізація (модулі 3, 5, 9, 11 — та сама сторінка, вкладки 2D і 3D)
python -m web.server
```
